# KAI 智能体与 WorkBuddy 专家对比

核查日期：2026-09-07。KAI 依据当前仓库代码及已有发布记录；WorkBuddy 依据官方开放平台文档。没有做同题实测，也未审查 WorkBuddy 私有运行时代码，因此不推断双方使用同一 SDK，不给出效果、速度或成本排名。

## 判断

两者在能力组织上高度相似：角色指令规定职责，Skill 保存可复用做法，工具/连接器提供实际执行能力，主智能体按职责委派子智能体。WorkBuddy 把这一结构包装成更容易理解的“专家”和“专家团”；KAI 同时承担智能体开发、发布和运行管理。

因此可以保留现有运行架构，把面向使用者的入口做得更明确。是否“专业”，最终取决于业务方法、资料质量、工具能否完成任务、交付标准和验证结果；给通用助手换名字与头像，不能保证专业效果。

## 对应关系

| 维度 | KAI 当前实现 | WorkBuddy 官方定义 | 判断 |
| --- | --- | --- | --- |
| 单个角色 | `agent.yaml`、系统提示词、Skills、工具与模型配置 | 专家插件包含 Agent Markdown 定义、市场信息和可选 Skills [1] | 都是角色与能力的组合；文件格式不相同 |
| 协作组织 | 主智能体通过别名和职责绑定固定版本子智能体 | 专家团声明主理人、成员；公开规范要求跨成员信息经主理人中转 [2] | 都支持以主角色组织协作 |
| Skill | `SKILL.md` 与资源目录，发布时快照与内容哈希 | `SKILL.md`、参考资料、脚本、模板 [3] | 业务方法和部分资源有迁移价值，需要检查运行依赖 |
| 外部能力 | 内置工具、MCP、自定义工具，编译与运行策略共同约束 | 连接器支持 MCP + Skill 或 CLI + Skill [4] | 可复用部分服务；鉴权、工具名称和运行环境仍需适配 |
| 使用入口 | 任务选择器、智能体列表、配置与试运行 | 专家卡片提供职责、推荐任务与召唤入口 [1] | KAI 可以进一步突出任务和交付物 |
| 配置复杂度 | 模型、权限、依赖版本、发布配置较多 | 专家作者不自行声明内置工具，系统统一分配 [1] | KAI 可用默认模板收起高级项 |
| 运行前准备 | 已有能力目录校验、依赖检查与运行前校验 | 声明依赖后，召唤前引导连接所需 MCP/连接器 [2] | 后端校验可转化成用户能理解的准备清单 |
| 版本与运维 | 草稿编译、不可变发布、固定依赖、评测、审计与运行事件 | 公开格式声明插件版本；本次材料不足以确认内部发布门禁与审计实现 | 不应将文档未披露等同于没有能力 |

## KAI 已具备的基础与需要补足的部分

当前编译器把模型、系统提示词、Skills、工具、子智能体职责与权限编译为运行契约。子智能体治理器要求引用固定版本，并限制并发及委派层级，当前不支持嵌套委派。相关实现见 `src/harness/studio/compiler.py`、`src/harness/runtime/subagent_governance.py`。

产品入口已经在向“专家团”靠近：父智能体中有“协作角色”，内部子智能体默认不进入普通卡片列表，也可以引用独立智能体。这个结构足以承接团队式呈现，不必为了改名称再做一套成员管理模型。参见 `docs/subagent-entrypoints-deployment-174.md` 和 `web/harness-console/src/components/agent-studio/agent-studio-workbench.tsx`。

已有失败记录说明，角色名称与执行能力还需要校验。`docs/unmetered-agents-174-release-20260907.md` 记载过多个分析角色绑定同一个只具备 Read/Glob/Grep 的 helper，却被委派拉取 MCP 数据、写文件或计算的任务。这是该发布记录中的具体案例，不能据此认定所有当前智能体都如此。它提示我们：配置“职责”时，应同时验证所需工具和输出条件。

例如，把“公文写作”呈现为“公文起草专家”时，可以明确：需要参考材料和目标文种，交付正文及 Word 文件；运行前检查文档生成工具可用。验收应包括事实依据、文种格式、文件能否正常打开，而不只看回复是否像公文。

## 建议的演进顺序

1. **完善专家卡片**：展示擅长任务、所需输入、交付物、适用边界和三个典型任务示例。普通用户先选任务，配置者再展开模型和权限。
2. **完善专家团详情**：展示主理人、各角色职责、输入来源和负责的交付部分。复用已有父子关系；内部角色继续跟随父智能体管理。
3. **把失败前移到准备阶段**：把缺少连接、未授权、工具与职责不匹配、依赖版本不可用转换成逐项可修复的问题。针对当前失败案例，优先检查委派目标是否具备所需工具。
4. **用真实样例验证专业性**：为公文写作、舆情分析等现有智能体分别维护标准任务、缺材料任务、工具失败任务与交付检查。比较单智能体与专家团的结果质量、时长和重复劳动，再决定是否增加角色。

以上为后续建议，本次未修改智能体配置、名称或协作逻辑。

## 包迁移的可行性

可以设计“导入 WorkBuddy 专家包”的适配器，但不能承诺 ZIP 直接兼容。可映射的内容包括角色 Markdown、Skills 资源、主成员关系和展示资料；需要重新处理 MCP 凭据、工具权限、模型选择、脚本依赖，以及 KAI 的固定版本引用。建议先导入为草稿，给出无法映射字段与依赖清单，通过试运行和评测后再发布。

这属于新功能设计，当前仓库并未因本次分析新增 WorkBuddy 专家包导入能力。
