# 174 长期记忆 P0/P2 发布与验收

发布目录：`/data/axis-memory-v2-20260908-1640`。入口：[记忆设置](http://172.20.109.174:3501/settings/memory)。

## 已实现

- **P0**：运行时按本轮问题检索；关键词与语义混合排序；取消最近 20/1000 条的召回限制；按完整条目装配 4000 字符预算，超长内容改为 `read_memory` 引用；旧文本转为待确认候选；统一 4000 字符写入上限；精确去重；Claude/Codex 均接入 `search_memory`、`read_memory`、`propose_memory`；范围包含租户、用户及智能体 owner/name。
- **P2**：成功任务结束后，从原始用户输入提取偏好、项目事实、实体、决策；候选带原文证据、主题、条件和替代关系；默认待确认；确认纠正时，以版本校验在同一事务中生效新条目、撤销旧条目及旧向量。相同条件才可替代，不同条件分别保留。
- 候选提取有持久任务、租约、失败重试和成功 Run 对账；提取任务完成不等于记忆已确认。编辑、删除和到期使旧向量失效；缺失或版本不匹配的向量由后台重建。删除会阻止较早提取任务重新写入。
- 同一轮工具先提出候选、后台后识别到纠正时，可补齐候选的替代关系，而不因精确去重丢失关系。工具也可显式传旧条目 ID 和版本。

## 为什么不需要独立向量数据库

仍是原 PostgreSQL 18.1 实例、原连接和原数据卷。pgvector 0.8.6 是加载进 PostgreSQL 的扩展，不是另一个数据库服务。正式部署没有新增向量服务端口。

```text
用户陈述 → 后台提取候选 → 用户确认 → memory_entries（正文、状态、权限、来源）
                                      ↓ shdata-bge-m3
                                memory_embeddings（1024 维、模型、条目版本）

新问题 → shdata-bge-m3 → PostgreSQL 余弦相似度 + 关键词召回
                     → 范围/状态/版本复核 → 完整条目预算装配 → 对话模型
```

`memory_extraction_jobs` 也在同一数据库。正文和向量用外键关联；删除和替代不需要跨数据库同步。向量是可重建数据，Memory Bank 的正文、确认状态和权限是权威记录。[pgvector 官方说明](https://github.com/pgvector/pgvector#readme)支持在 PostgreSQL 中存储向量、执行 JOIN、精确检索及近似索引。

首期使用**权限范围内的精确余弦检索**，尚未创建 HNSW/IVFFlat 近似索引。数据增长后可在同一 PostgreSQL 增加索引；需要先验证范围过滤下的召回率和延迟。当前关键词部分仍在应用侧扫描该用户/智能体的有效条目，没有完成大规模性能评测。

## 操作验收案例

使用同一登录账号、同一个智能体，在正式对话中操作，不使用智能体构建页的预览/试运行。建议选择项目中可正常对话的模型。测试前强制刷新页面，记下智能体名称；记忆设置页按该名称查看记录。为观察确认流程，使用“逐条确认”的保存策略。

### 1. 提出长期偏好

在新会话 A 发送：

> 我的项目代号是“银杏验收”。以后这个项目的进展汇报，我偏好先给结论，再列三条关键进展，最后列风险。请记住这个长期偏好。

任务成功结束后，等待约 30–120 秒，在记忆设置页点击“刷新”。模型提取延迟和队列繁忙会延长等待时间。

预期：出现“待确认”候选，内容保留“银杏验收”这个适用范围；后台提取的候选可以展开“查看来源证据”。如果智能体已通过记忆工具直接提议，来源显示“Agent 提议”，不一定有原文摘录。在确认前，用页面“查找相关记忆”不应召回此候选。

点击“确认保存”，应变成“使用中”。

### 2. 验证同义问题和跨会话召回

先在记忆页查询：

> 银杏验收的工作汇报应该按什么顺序组织？

预期：返回已确认的偏好和来源、版本。

再新建会话 B，选择同一智能体，发送：

> 银杏验收本周完成了接口联调，报表还在测试，存在交付延期风险。请按照我的惯用结构整理一份进展汇报。

预期：结论 → 三条关键进展 → 风险。新会话用于区分长期记忆与同一会话的上下文。不要在新问题中重新告诉模型原先的顺序。

### 3. 验证纠正不会直接覆盖

在会话 B 继续发送：

> 纠正一下：以后银杏验收项目的进展汇报改成先列风险，再给结论，最后列三条关键进展。适用范围不变，请替代以前的顺序。

刷新记忆页，预期出现带“确认后替代原记忆”说明的新候选。未确认前原记忆继续有效；确认后原记忆不再召回，新记忆生效。

再新建会话 C 发送：

> 请按我的偏好组织银杏验收项目的汇报提纲。

预期：风险 → 结论 → 三条关键进展。

若模型将“适用条件”提取成不同条件，系统会拒绝强行替代；页面可分别显示候选。先核对条件和证据，不要把条件不同的事实视为同一条。

### 4. 验证删除

删除本案例创建的“使用中”记忆，再用页面重复同义查询，预期不返回该条目。等待一个后台处理周期后刷新，旧提取任务不应重新创建它。

另开会话 D 问“银杏验收项目的汇报顺序偏好是什么？”：模型不应声称从记忆知道已删除的偏好。模型可能碰巧给出常见模板，因此**以记忆检索无结果为确定性验收依据**；旧会话中仍有聊天历史，不适合验证遗忘。

## Worker 并发调整

| 参数 | 调整前，每个 Worker | 调整后，每个 Worker |
|---|---:|---:|
| `HARNESS_WORKER_CONCURRENCY` | 4 | 8 |
| `HARNESS_WORKER_DEFERRED_MAX_ACTIVE_RUNS` | 2 | 8 |
| Worker 数量 | 3 | 3 |

任务调度总上限由 12 提升为 **24**。延迟沙箱参数只在启用相应运行模式时起作用，同时设置为 8 以免成为额外瓶颈。部署实际逐个核实三个 Worker 的两个配置均为 8。代码可配置范围为 1–32，但本轮未把它调到最大。

机器实测 104 个逻辑 CPU、约 251 GiB 内存，可用约 136 GiB。平台配额执行原本关闭，本轮保留。24 是配置上限，不代表已经测得 24 路稳定吞吐；模型网关、远程沙箱、任务内子智能体和同会话串行约束仍会影响实际并发。本轮未发起 24 路真实模型压测。

## 运维与恢复

服务器发布目录保留：原容器配置快照、`compose-files.json`、完整 `compose-command.json`、`compose-memory.json`、运行配置文件、86 MiB 数据库备份、前后端镜像和构建源码。配置文件含凭据，权限为 0600，不要直接打印或拷入版本库。

使用服务器上的 `compose-command.json` 中完整参数调用 Docker Compose；它包含原 `.env.production` 和全部历史覆盖文件。不能仅用基础 compose 文件重启，否则会丢失本次记忆和并发配置。

仅恢复并发时，把 `compose-memory.json` 的 worker 环境变量恢复到 4 和 2，再通过完整 Compose 命令仅更新 worker，保留 3 个副本。无需回滚数据库。

旧 Web 容器 `axis-web-20260908-settings` 已停止保留；旧 API 镜像及配置快照仍在。应用版本恢复应保留新增数据库结构；若已产生 `superseded` 记录，旧版 Memory Bank 的状态枚举需要兼容处理，不能直接降库或用旧备份覆盖上线后的业务数据。优先通过当前版本关闭自动提取、保留原有记录来隔离故障。
