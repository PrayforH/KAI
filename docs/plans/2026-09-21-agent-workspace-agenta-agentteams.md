# 智能体工作区：Agenta 交互落地与 AgentTeams 借鉴方案

日期：2026-09-21。范围：当前项目的智能体页面，以及它与项目任务的连接。本文区分本轮已实现交互和下一阶段团队协作设计；团队编排尚未实现。

## 设计结论

Agenta 适合指导单智能体的构建、试跑、评测和接入体验；agentscope-ai/AgentTeams 适合指导多人、多智能体共同执行任务时的分工、交接、人工干预和恢复。把两类经验落到不同工作层级，避免智能体页面再次成为一个从头到尾滚动的长表单。

智能体页保留四个工作环节：运行与诊断 → 改进实验 → 评测验收 → 发布与效果。Playground 负责配置与试跑；自动运行、集成、评测集、经验库是可独立访问的能力和资产。每个页面只呈现当前环节的主要动作，通过任务、候选和版本标识跳转到下一环节。

## 本轮吸收的 Agenta 交互

| 方向 | 当前项目的实现 | 验收重点 |
| --- | --- | --- |
| Playground | 复用构建对话、配置、效果测试的现有工作台；支持从评测用例填入输入框，再编辑和发送；保留草稿修订、会话隔离、附件、停止、重新试跑和修改建议确认 | 选择用例不会自动运行；发送仍经过保存和版本检查；修改配置后不会误续旧配置会话 |
| Trace | 将试跑原始事件组织成时间线与详情；按模型、工具、审批、异常筛选；生产诊断和评测用例复用同一查看器 | 读取失败与空数据分开；后端继续检查运行所有权；显示的是事件证据，未伪造完整 span 树或未采集的指标 |
| Eval | 同一用例的基线与候选并排，按改善、回归、证据缺失筛选；点开可比较失败断言、耗时、工具和两侧 Run Trace | 缺失的一侧不能判定为改善；未完成评测不能视作通过；结果仍由服务端报告决定 |
| 批量审批 | 同一试跑内多项待审批工具调用可勾选处理；展示工具、风险、参数、原因和有效期；逐项请求、逐项反馈，部分失败可以只重试失败项 | 不批准未选项或过期项；只读用户不能提交；不会将一次批准改为永久授权；此处是工具审批，候选发布审核仍独立 |
| Cron | 当前智能体的 schedule trigger 增加五段 Cron 与 IANA 时区，复用主线自动化解析器；保留旧 intervalSeconds；显示实际下次执行时间 | 两种计划互斥；校验无效时区/表达式；并发调度仅领取一个执行时隙；执行当前环境部署版本 |
| 集成目录 | 按本智能体已声明/全部可见能力筛选 MCP 和内置工具；可搜索名称、用途、工具；展示目录状态、风险和能力明细 | 区分“已声明”“需检查授权”“预检通过”；不展示凭据字段，不把注册目录等同于连接可用 |

自动运行从发布页面中独立出来，继续使用已有的环境路由、工作负载凭据与触发器控制面。它不同于主线全局自动化任务：全局自动化当前没有绑定任意智能体的模型字段，不能仅通过前端筛选就声称是在调度当前智能体。

参考：[Agenta Agents](https://agenta.ai/docs/concepts/agents)、[Automations](https://agenta.ai/docs/concepts/automations)、[Tools and integrations](https://agenta.ai/docs/concepts/tools-and-integrations)。以上是结合本项目接口设计的实现，不是对 Agenta 代码或界面的逐像素复制。

## AgentTeams 最值得吸收的部分

用户明确指定的项目是 [agentscope-ai/AgentTeams](https://github.com/agentscope-ai/AgentTeams)。其核心角色包括 Human、Manager、Worker、Team 和 Team Leader；团队将分工组织为可复用协作单元，消息与交付物可以被人检查。[官方概览](https://github.com/agentscope-ai/AgentTeams/blob/main/docs/overview.md)

### 1. 可复用团队和稳定职责

建议新增 TeamDefinition，保存负责人、角色说明、成员智能体版本引用、交接条件和共享资产范围。它是协作配置，不能和现有用于权限/共享的团队空间直接画等号。

智能体详情呈现“参与的团队”“承担角色”“输入/输出契约”和最近的交接结果。团队建立与执行放在项目工作台，避免在每个智能体页重复配置完整团队。

### 2. 提交与验收分开

Worker 的运行结束只表示执行结束。建议在业务任务层增加提交记录，包含提交 ID、Agent 版本、Run ID、产物引用及哈希、验收标准和验收决定。审核必须绑定当前提交；发生重做后，旧页面不能接受新的交付。

AgentTeams 的工作流接口区分任务节点、交付信息和提交标识，可以作为交接契约参考。[工作流 API](https://github.com/agentscope-ai/AgentTeams/blob/main/docs/zh-cn/usage/project-workflow-api.md)

这与现有候选审核的 reportHash/revision 思路一致，但不能直接把候选版本审核拿来充当业务任务验收。前者决定是否发布能力，后者决定一次交付是否合格。

### 3. 任务板与依赖视图

建议项目执行页默认显示任务板：待执行、进行中、待验收、需返工、已完成；依赖图作为另一种视图。点节点打开负责人、阻塞原因、输入、交付物、验收记录和 Trace。管理者应能快速回答“谁在做、卡在哪里、下一步是什么”。

AgentTeams Dashboard 的结构化运行消息、工作流/确认块和按需打开的线程详情值得借鉴；基础设施资源卡片更适合管理后台。[Dashboard](https://github.com/agentteams-group/agentteams-dashboard)

### 4. 有明确语义的人工干预

建议分别提供暂停派发、取消某次运行、要求返工、变更负责人和重新规划。每个动作记录操作人、理由、旧修订和新修订。不要用一个含糊的“暂停”覆盖所有语义。

AgentTeams 文档特别说明项目暂停停止新任务派发，进行中的任务仍可完成。这种明确边界值得采用。运行时恢复能力需要逐内核检查：不能把某一内核的 checkpoint 接口视为所有模型执行都能从任意步骤恢复。

### 5. 共享交付物与可追溯经验

共享上下文优先使用受控对象存储中的文件引用、摘要和产物版本，不让成员反复复制整段对话。采用现有 MinIO、Artifact、Session、Run 和权限体系，给文件补充任务/提交归属。

业务验收失败 → 记录失败类型与证据 → 转为评测样本 → 发起单智能体改进 → 验收新版本 → 在团队任务中观察。团队执行提供真实问题来源，单智能体飞轮负责验证和改进。

### 6. 按能力统一多运行时

保留现有运行时路由，补充团队调度需要的能力声明，如可取消、可续跑、支持工具审批、可恢复检查点。角色选择不能只依赖名称或模型偏好；调度前验证工具、权限和运行环境是否满足任务。

AgentTeams 在统一控制面下管理不同运行时，同时使用网关身份与共享存储，架构上可借鉴其“协作控制面与执行内核分离”的方式。[架构](https://github.com/agentscope-ai/AgentTeams/blob/main/docs/design/architecture.md)

## 建议开发顺序

| 阶段 | 交付 | 必须通过的验收 |
| --- | --- | --- |
| A：本轮单智能体交互 | Playground、Trace/Eval、工具批量审批、Cron、集成目录 | 真实接口连通、权限与错误态、部分失败反馈、旧入口兼容 |
| B：最小团队协作 | TeamDefinition、角色版本引用、项目任务板、任务提交和验收 | 两个智能体围绕一个任务交接；失败能返工；重复提交/旧验收不能覆盖新结果 |
| C：协作可控 | 依赖图、暂停派发、改派、取消、状态历史 | 重启后无重复派发；跨团队不可读取；运行中任务的处理语义明确 |
| D：团队连接飞轮 | 验收失败转样本、团队效果观察、角色级经验 | 样本来源可追溯；评测与真实业务运行分开；未验证经验不自动注入 |

阶段 B 的数据模型建议：TeamDefinition、TeamRun、TaskAssignment、TaskSubmission、TaskDecision、CollaborationEvent。TeamRun 冻结团队修订与各成员版本；TaskAssignment 有负责人和依赖；TaskSubmission 有不可变产物引用；TaskDecision 绑定 submissionId；CollaborationEvent 有稳定序号和操作者。

这些是本项目下一阶段建议，不代表 AgentTeams 的同名内部类型，也不代表本轮已新增团队编排能力。暂不引入另一套 Matrix、Higress、Kubernetes CRD、对象存储或完整 AgentTeams runtime；先复用现有平台验证一条真实协作链。
