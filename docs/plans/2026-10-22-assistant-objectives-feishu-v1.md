## 第一版用户功能

1. **我的助理入口**：事项列表、需要决定的事项、最近交付；继续沿用 KAI 当前主题、侧栏和任务工作区。
2. **持续事项**：名称、目标、关联的真实 Project、负责 Agent、检查频率/时区、停止条件、通知偏好、状态。可创建、编辑、暂停、恢复和结束。
3. **持续上下文**：事项摘要、用户补充和执行结果持久保存；每次执行引用同一事项，保留独立 Session/Run 和产物。更新带 revision，避免旧结果覆盖新要求。
4. **后台跟进**：用户手动执行、到期唤醒、已接入的事件触发；同一事项默认串行，跨事项受租户并发限制。关闭网页仍继续。
5. **结果与待决策**：清楚区分正在执行、等待输入、等待审批、执行失败、已交付和事项结束。站内收件箱显示来源和原任务链接。
6. **飞书连接**：管理员配置企业自建应用；用户在已登录 KAI 中生成短期绑定码，向机器人发送后绑定自身 open_id。允许解绑和关闭通知。
7. **飞书消息入口**：绑定用户的私聊可创建事项、查询状态和继续事项；歧义时返回选择卡片。初版不监听任意群聊、不转发私有上下文到群。
8. **飞书结果与确认卡片**：重要变化和交付通知发给已绑定本人；确认操作绑定接收者、事项版本和一次性操作令牌，重放不重复执行。权限敏感的工具批准仍走现有审批服务。

飞书入口、网页入口调用同一应用服务。第一版不通过飞书接入替代 KAI 登录，不把机器人应用权限当作用户文档授权。文档/日历用户 OAuth 可按具体业务工具另接，首版的消息闭环不需要索取用户全量权限。

## 飞书部署方式

选择官方 Python SDK 长连接，独立进程接收事件/卡片回调。适合 79 出网条件，不依赖开放公网 Webhook。仅适用于企业自建应用。接收处理器仅验证、去重并持久入队，3 秒内返回，不在回调中等待模型。

长连接为集群投递而非广播；开发与生产不能使用同一应用同时消费真实消息。环境使用独立应用或确保仅一个活动消费者。应用凭据保存至既有凭据机制，日志只记录事件 ID、状态及安全错误码。

官方依据：[长连接事件](https://open.feishu.cn/document/server-docs/event-subscription-guide/event-subscription-configure-/request-url-configuration-case.md)、[长连接回调](https://open.feishu.cn/document/event-subscription-guide/callback-subscription/step-1-choose-a-subscription-mode/configure-callback-request-address.md)。后续具体消息、卡片和 token 协议以逐项读取的官方文档为准。

## 架构与对象

沿用 `Project → Session → Run`，新增 `Objective`（持续事项），Project 为真实业务归属；事项不是 Session 的别名。新增模块集中在 `harness/assistant`，按 models / repository / service / controller / api 分层；渠道适配放 `harness/feishu`，不让业务服务依赖 SDK DTO。

- Objective：租户、用户、项目、Agent、目标、状态、revision、检查计划、下一次检查、摘要、通知规则、预算。
- ObjectiveExecution：确定性触发键、捕获的事项版本、Session/Run 引用、结果与重试状态。
- ObjectiveEvent：用户补充、分派、失败、交付、暂停/结束等不可变记录。
- AssistantInbox：重要变化/待决策、来源、已读、投递状态和去重键。
- FeishuBinding：应用/租户/open_id 与 KAI user 的映射，绑定码只存摘要、有效期与单次消费状态。
- ChannelDelivery：投递 ID、接收对象、重试、外部 message_id；发信去重与事件消费去重各自独立。

事项状态只表示 active / paused / completed / cancelled；运行中、等待审批等由关联 Run 派生，避免两个状态机相互覆盖。事项完成需明确完成条件或用户决定，不从 Run succeeded 自动推断。

## 可靠性与权限约束

- 先持久化执行意图再提交 Run，使用 `objective_id + trigger_key` 幂等。检查租约及版本，崩溃后从执行意图恢复。
- 每次唤醒重验账号、项目和 Agent 权限；事项授权仅收紧现有能力上限。不能仅传一个 readonly 字段却仍开放写工具。
- 运行采用事项版本快照。修改指令不篡改旧执行记录；需要转向时沿用现有 steering 协议并记录接收状态。
- 暂停禁止新调度但保留已运行任务；“停止整个事项”撤销未来唤醒并请求取消当前 Run，UI 等待真实终态。
- 各读取和变更都限定 tenant/user；飞书 actor 通过服务器绑定解析，不接受消息中的用户 ID 或角色声明。
- 通知仅发给主动绑定且启用的本人；群消息与共享事项后续独立设计。
- 不在 HTTP 请求、事件回调或内存定时器中承担唯一执行状态；生产实现必须持久化。

## 迭代与证据

### 0：同步完整基线

检查两端镜像/配置/迁移，备份 79，传输精确镜像，验证迁移兼容，预览健康，切换应用；复核账号、历史、产物计数、项目与构建功能。迁移失败保持原服务；应用失败恢复原镜像，兼容新增表不破坏原数据。

### 1：事项纵向闭环

实现持久模型、迁移、带版本的 API、现有 Run 适配和 Worker 控制器；前端实现列表、详情、编辑、执行、停止及收件箱。验证跨用户隔离、到期触发、重试幂等、崩溃恢复及终态展示。

### 2：飞书闭环

实现连接配置、绑定码、长连接进程、收件去重、消息路由、通知发件箱和卡片决策；优先用官方 SDK 类型做契约测试，配置真实自建应用后验证一条完整链：网页事项 → 飞书通知 → 本人卡片操作 → 同事项状态更新。

### 3：79 小范围迭代

先开放给试点用户，用内控材料跟进或舆情专题一个场景验证。修正重复提醒、事项上下文丢失、执行状态误报和长任务停止问题。记录真实验收证据，不用模拟成功代替飞书连通或真实 Agent 运行。

完整 174 基线已在 79 同步且原数据保留；首版事项能跨网页会话持续运行；结果和待决策可见；飞书本人绑定、消息入口、通知和确认链路可验证；后端与前端必要测试和构建通过；具备版本、迁移、回滚与部署报告。缺少真实应用凭据时飞书只能标为待连接，不能宣称已上线可用。
