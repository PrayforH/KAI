KAI 个人助理域架构

说明个人助理（主助理与专职子助理）在 KAI 中的产品边界、控制面位置、通道与会话、职责与记忆，以及它如何使用本人 Computer。本文与《KAI 云电脑 / Computer 架构》互为姊妹篇，不互相替代。

阅读约定

平台总览把「部署地址由配置提供，不使用主机编号代表产品环境」写进了架构原则。分支内大量实施与验收文档仍以 79、116 等主机称呼具体部署。本文在引用这些主机时，只把它们当作文档中的部署实例，不把主机编号升格为产品环境名称。

1产品定位与边界

KAI 是面向智能体构建、任务执行与运行治理的工作平台：把对话、Agent Studio、模型与能力管理、知识库、长期记忆和产出物放在同一工作台，由统一控制面管理运行状态、权限、审批和发布。当前平台版本在 README 中记为 0.3.1。

出处：README.md — 平台定位、主要能力与文档入口。

本文所说的个人助理域，是该平台之上、按账号归属的常驻助理体验：一名用户拥有主助理，并可配置多名专职子助理（文档与界面中常称为 Bot）。它复用 Harness 已有的 Session、Run、事件、审批与模型路由，而不是另建一套发布系统或任务引擎。

出处：src/harness/assistant/__init__.py — 模块说明为“Persistent responsibilities coordinated through existing Harness runs.”

出处：src/harness/assistant/models.py — 开篇说明个人助理契约与通道无关；Objective 的生命周期不得从单次 Run 终态推断。

1.1与领域 Agent 包不是同一对象

docs/domain-agents.md 描述的是可版本化的业务 Agent 目录（agents/*/agent.yaml、Skills、Tools、评测与打包发布）。那是 Agent Studio 的生产形态：解决「如何安全、稳定、可验证地运行一个领域 Agent」。个人助理会复用已发布的能力模板来实例化专职子助理，但不等于领域 Agent 包本身，也不引入第二套发布体系。

出处：docs/domain-agents.md — 领域 Agent 是可版本化目录，平台升级与业务迭代相互独立。

出处：src/harness/assistant/models.py — Specialist：「持久专职子助理：复用已发布能力模板的实例配置，不引入第二套发布系统。」

1.2与 Studio 团队空间不是同一对象

团队空间解决的是 Agent Studio 里「可复用定义」与「用户运行记录」的安全边界：空间只保存对已发布、不可变 Agent 版本的授权引用，不复制 Agent，也不改变所有者。成员可以运行同一共享 Agent，但不能读取彼此的线程、Run、审批、产出物或记忆。个人助理域是账号内的主助理 / 子助理与本人会话，不能用团队空间模型来解释。

出处：docs/team-spaces.md — 资源模型、RBAC 与运行隔离；Web 入口为 /studio/spaces。

1.3产品入口

网页入口在文档中写为 /assistant。控制面 API 前缀为 /v1/studio/assistant，供 Web 与已认证的通道适配器共用。本人私聊的稳定线程标识是 kai-personal-assistant-v1。主助理在界面上另有展示用身份 specialist_primary_*，代码明确写明：这是呈现身份，绝不是授权授予。

出处：src/harness/assistant/api.py — 「Owner-scoped assistant API, shared by Web and authenticated channel adapters。」前缀 /v1/studio/assistant。

出处：src/harness/assistant/constants.py — PERSONAL_ASSISTANT_THREAD = kai-personal-assistant-v1；primary_specialist_id 为展示身份。

分支文档多次记载 79 环境的助理入口为 https://172.20.105.79:3543/assistant（自签证书需手动信任）。116 环境在 2026-11-04 的验收文档中把 AUTH_PUBLIC_URL 记为 https://172.20.109.116:3543，同日验证 / 与 /login 返回 200；2026-11-10/11 的能力对齐文档则记录 116 上 /、/assistant 等路由为 200。未在该提交中见到其他对外产品 URL，本文亦不补写。

出处：docs/plans/2026-11-05-kai-computer-demo-pipeline.md — 写明 79=https://172.20.105.79:3543/assistant。

出处：docs/results/2026-11-04-116-acceptance-host.md — 116 主机、AUTH_PUBLIC_URL 与当时已部署服务。

2角色与对象

2.1用户

个人助理对象按 tenant_id + user_id 归属。创建专职子助理时，租户与用户由身份推导，API 不接受客户端伪造。电脑同样按该二元组唯一，见姊妹篇。

2.2主助理

主助理是本人跨通道私聊的前台入口，使用稳定线程 kai-personal-assistant-v1。专属页面在 2026-10-30 的托管计划中被要求「不套用通用助手任务过程界面」，并以结果优先卡片组织「需要你处理 / 正在推进 / 已交付」。后续对话形态改造把主助理页做成气泡会话，左栏将主助理置顶，专职子助理列为独立会话入口（/assistant?bot=）。

出处：docs/plans/2026-10-30-kai-assistant-managed-goal.md — 阶段 1 专属主助理页面与引用回复；第三轮 C4/C5 左栏与子助理独立会话。

2.3专职子助理

专职子助理是持久实例，有自己的名称、slug、描述、所绑定的已发布 agent_name@version，以及与身份分离的结构化配置。配置状态机为 draft / needs_input / validating / ready / active / paused / blocked / archived。文档强调：保存不等于验证，缺项不得启用。

转交回执 assistant_handovers 区分发送、接收与执行：sent → received → applied / pending_input（后续还出现 executing / failed）。按 message_id 幂等，重放不重建。子助理可被挂上职责（Objective）；定时能力属于职责，不属于头像或名称。

出处：docs/plans/2026-10-30-kai-assistant-managed-goal.md — 阶段 3：specialists、状态机、转交回执、凭据只写引用。

出处：src/harness/assistant/models.py — Specialist、SpecialistStatus、SpecialistHandover 与 HandoverStatus 定义。

2.4在会话中 @ 子助理

在助理面输入 @ 可以提起可访问的助理，写入行内 @名字，可多个；发送时才派发。服务端用 POST /specialists/{id}/messages 把正文交到目标原会话，目标与线程由服务端解析，并回到来源会话的幂等回执（「已发送消息给 …」）。这是本人助理面里的提及与交办，不是多人群聊。

出处：docs/plans/2026-11-03-kai-bot-vault-goal.md — P14：助理面 @ 提及、行内插入、回执；不得改变普通任务面行为。

出处：src/harness/assistant/api.py — send_specialist_message / send_mention_message 的契约说明。

3在 KAI 控制面中的位置

当前实现的平台组件在 docs/architecture.md 中列为：Web 工作台、同源 BFF、FastAPI 控制面、Worker、运行时适配层、PostgreSQL/pgvector、Redis、S3 兼容对象存储，以及任务用的 Sandbox / MCP。浏览器不持有服务密钥。控制面保存 Session、Run、Agent 版本、权限和耐久事件；Worker 消费队列并调用运行时。

出处：docs/architecture.md — 组件职责、执行链路与三种运行时内核。

助理域在此之上增加了 src/harness/assistant 的仓库与服务、主人范围 API，以及独立的飞书 / 微信适配服务（文档中的 79 部署常把 feishu、weixin 列为与 api/worker/web 并列的容器）。后台执行仍然走既有 Run 与事件投影（AG-UI / SSE），而不是另造调度或 Ticket 存储。

出处：docs/plans/2026-11-03-assistant-semantic-routing.md — 「复用现有发送/接收时间线与 SSE」「不另造调度、Ticket 或 Vault」。

与一次性 Sandbox 的关系

架构说明中的 Sandbox 是任务执行隔离环境，提供方可随部署变化。个人助理的持久 Computer 在源码中被明确写成与「一次性 Run 沙箱」不同的对象。两者如何并存、何时改走 Computer，见第 8 节与姊妹篇。

4会话与通道

2026-10-27 的差距分析记载：KAI 已有飞书、微信、网页本人私聊共用会话，并支持图片、文件、语音和组合消息；本人通道主动采用同一线程，并已验证刷新续聊。同文写明：「未来群聊必须增加独立受众边界」「未来群聊不继承本人完整聊天镜像」——这是当时的设计约束，不是已实现的群聊架构。

出处：docs/plans/2026-10-27-assistant-dot-bot-computer.md — 多端身份与上下文现状，以及群聊受众边界的前瞻约束。

通道执行控制 V1 已实现并部署到 79：飞书 / 微信文字私聊可用「进度」「停止当前任务」「/补充」等读取或干预当前 Run；控制目标先持久化再变更；微信控制与普通聊天独立队列。该轮发布时尚未启用持久 Computer。状态查询只报告执行阶段，当时尚未推送逐工具实时进度。

出处：docs/plans/2026-10-27-assistant-dot-bot-computer.md — 通道执行控制 V1 的范围与边界。

2026-11-04 的首屏加载计划要求：IM 状态在对应会话历史就绪后再挂载；电脑按钮首屏不请求状态，桌面占用仅在打开时读取，并去掉「上次打开偏好导致的自动重连」。

出处：docs/plans/2026-11-04-assistant-startup.md — 首屏加载、IM 挂载时机与电脑延迟连接。

5交办、提及与 1:1 通路

交办与托管是分阶段补齐的。2026-10-30 的托管计划把 Objective 扩展为可绑定原线程续跑，区分 autonomous / follow_only；互斥派发避免用户直聊与后台托管抢同一线程；检查点与 assistant_manage_work 等工具用于纳管既有任务。递归委派被收口：委派工具只注入个人助理协调线程，后台 objective 执行线程不再携带委派工具。

出处：docs/plans/2026-10-30-kai-assistant-managed-goal.md — 阶段 0–2 与第二轮 R 系列：托管、检查点、预算、skipUnchanged。

5.1当前 1:1 通路：创建与发送是两个独立工具

2026-11-03 当天曾先上线过主助理结构化路由：网页主会话里用 assistant_route_message 在 dispatch / direct / clarify 中做一次分类再派发。该方案有过 79 发布记录，但不是本分支此后记载的现行 1:1 路径。

出处：docs/plans/2026-11-03-assistant-semantic-routing.md — 当日早些时候的路由协议与 79 发布记录；后文已被自主执行方案取代。

同日稍后的「Bot 自主执行」方案删除强制 assistant_route_message 分类与工作流门控。验收文档写明：联系人创建和消息发送拆为 assistant_create_specialist 与 assistant_send_message；按每次操作的 request_key 做投递幂等，不限制一轮只能做一个业务决定，也不规定工具调用顺序。创建联系人不会自动产生 Run、职责或定时规则；是否派工由模型另行调用发送工具。平台仍校验权限、收件人、来源和输入完整性。主会话仍是统一交互入口，子助理的补充、确认与授权投影回原消息位置。

现行代码与上述验收一致：src/harness/assistant/messaging.py 向运行时注册的平台工具就是这两个名称，模块说明为「与业务规划无关的 Bot 生命周期和消息传输」；控制面「没有按轮次的计划、分类或工具门控」。79 验收记录还写明，运行镜像中已删除 routing.py，实页主 Run 使用目录查询和 assistant_send_message，「无强制路由工具」。

出处：docs/plans/2026-11-03-bot-autonomy-refactor.md — 取消强制分类；创建与发送为独立工具。

出处：docs/results/2026-11-03-bot-autonomy-79.md — 明确写出删除 assistant_route_message，拆为 assistant_create_specialist 与 assistant_send_message；镜像中 routing.py 已不存在。

出处：src/harness/assistant/messaging.py — PlatformTool 名称、创建不自动发送、发送回执与幂等。

不要和群聊路由混在一起

上述工具与第 2.4 节的 @ 提及，都是本人 1:1 助理面里把消息交到某个专职子助理原会话的通路，不是多人群聊里的接话或 @ 路由。群聊相关能力在本远程分支中仍未确认，见第 11 节。Codex 执行入口的平台派发工具，在被废止的路由计划里曾写「本轮不宣称支持」；之后未见确认接通，本文保持「未确认」。

6记忆、职责与日程

6.1长期记忆

平台记忆与知识在架构说明中是分开管理的：知识库绑定为任务提供检索；长期记忆按归属与作用域保存偏好、事实、实体和决策，使用关键词与向量混合召回。任务后自动提取是可选配置，架构说明写明默认关闭；启用后候选须经确认才参与召回。模型输出、网页与工具结果不能直接覆盖用户偏好。

出处：docs/architecture.md — 记忆与知识的默认边界。

个人助理侧通过 propose_memory 写入提案。2026-11-11 的对齐文档记录了两处修复：一是提案默认 pending，对话里补上确认卡片（调用 memory-bank/entries/{id}/confirm）；二是在会话曾读过外部内容时，必须附上用户原话 evidence_quote 作出处，网页或工具结果中的句子不能冒充用户原话。子助理领域记忆使用 specialist:{slug} 作用域，并在 79 做过写入、召回与跨 Bot 隔离验收。

出处：docs/plans/2026-11-10-assistant-parity-1-2-3-7.md — 长期记忆写入链路与按出处放行。

出处：docs/plans/2026-10-30-kai-assistant-managed-goal.md — R3 子助理领域记忆及 79 验收引用。

同一对齐文档还记录：79 的提取环境「本来已带 /v1、自动保存为 true」。这与架构说明中「任务后自动提取默认关闭」是不同层次的事实——前者是具体部署配置，后者是平台默认。本文不强行统一它们，只并列注明。

6.2Objective：职责、调度与预算

Objective 是跨 Run 存活的职责对象，含标题、要求、绑定的 Agent 版本、可选日程、ends_at、完成标准、通知模式和预算。执行记录带 triggerKey 命名空间，对齐文档将其显示为：定时 / 手动 / 飞书 / 委派 / 管理 / 演练（schedule:、manual:、feishu:、delegate:、delegate-specialist:、manage:、trial:）。

预算可限制每日或累计运行次数，以及在有真实计量时的 token / 费用上限；无计量时须诚实报告而不是记 0。skipUnchanged 使定时检查在无变化时不唤起模型。pause 停调度但不停在途执行，stop 会取消绑定 Run。共享桌面若被职责声明为需要，则按优先级 + FIFO 排队，且「对活 holder 仍不抢占」。

出处：src/harness/assistant/models.py — Objective、Budget、Schedule、Execution、Checkpoint、DesktopTurn。

出处：docs/plans/2026-10-30-kai-assistant-managed-goal.md — 预算、暂停/停止、桌面排队与 skipUnchanged。

6.3定时任务界面（116 已记录的进度）

2026-11-10 的定时任务计划把「任务」面板对齐到：重复 + 时间 + 有效期，覆盖单次/每天/每周/每月/每年；执行记录作为内页，带状态与触发类型筛选。文档记录 P0、P1a、P2 已在 116 落地；遗留包括：P1b 新建任务需要后端把 specialistId 透传到 POST /objectives（service 已支持，API 未暴露）；每双周与按任务选择推送渠道属于 P3，当时未做。能力对齐文档在「待办」中再次确认 P1b 仍缺该透传。

出处：docs/plans/2026-11-10-assistant-scheduled-tasks.md — 设计、分期与 116 发布记录。

出处：docs/plans/2026-11-10-assistant-parity-1-2-3-7.md — 待办仍列出 P1b。

7Vault 与个人 Skill

2026-11-03 的 Vault 计划把「设置内助理资料库」做成分类存储（全部 / 登录密钥 / 卡片 / 联系信息等）：搜索、新建、编辑、受控授权给某个 Bot、删除需确认。列表与接口只回脱敏元数据，密文不进模型与普通接口。授权写入 credential_ref；撤销或删除后即拒用。

该计划把能力分成四层，并如实标注第④层「已接工具」当时未支持：运行时没有工具消费 credential_ref。本取证提交中，未见后来文档宣布第④层已经接通，故本文仍按「未确认已接工具消费」处理。

8助理如何使用 Computer

产品模型在 2026-10-27 的方案中写为：「每个用户一台持久 Computer，多个 Agent 共用本人工作环境」。Computer 按 (tenant_id, user_id) 唯一。任务只申请执行租约；结束时释放租约、回收对应进程组，并不销毁电脑。

10与云电脑架构的关系

个人助理是控制与编排入口：理解用户意图、维护职责与记忆、把工作交到子助理或本人 Computer。Computer 是按用户持久化的执行与桌面环境，由独立的 Registry、租约、control 与 viewer 管理。二者在 79 的部署中常一起出现，但生命周期不同——关掉一次 Run 不应毁掉电脑，切换或接管电脑也不应改写助理的身份与聊天历史。

请配合阅读同目录中的 《KAI 云电脑 / Computer 架构》。
