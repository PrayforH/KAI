# 主助理按职责路由与派发

2026-11-03；基线43aefddc，实施于独立kai-weather-fix工作树。只部署79，IM暂缓，任务与项目保持原路径。

## 依据与取舍

DeepSeek官方研究原型将主Session路由、Executor执行、Decision持久记录与事件回传分开；原文见[角色与提示](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/004-prompts.md)、[领域流转](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/001-domain.md)、[授权](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/002-authorization.md)。本项目借鉴职责边界、短路由说明、服务端校验和无等待回传；不复制它的工具权限、定时器或另一套Ticket存储。用户已明确不要子助理重复确认任务，因此保留KAI的直接执行体验，区别于原型默认的大任务确认流程。

当前差距：主助理把天气归为简单问答而直接联网；目录只包含名称和状态，没有完整职责；普通派发可能再建Objective；仅提示词无法阻止派发后重复工具执行。

## 本轮协议

用户主会话消息 → 主模型阅读本人Bot职责目录 → 一个结构化决定 → 服务端派发 → 原子助理会话Run → 既有结果事件回主会话。

1. 名称、描述、可用性构成动态目录；它们是资料，不能覆盖平台规则。无天气关键词路由表，也不多跑一个前置分类模型。
2. 只对本人主助理的网页聊天启用。主模型以`assistant_route_message`选择dispatch/direct/clarify并给出简短、可审计的业务理由。明确匹配职责优先派发，即使用户没点名；没有匹配、用户明确要求主助理亲自做、助理管理等走direct；职责歧义或必要信息缺失走clarify。
3. 模型只能选现有Bot ID；服务端重新校验所有权、状态、配置及实际会话权限。派发原始输入与已有引用上下文，保留原会话Agent身份，不让模型重写用户要求或挑执行版本。
4. 决定通过现有Run EventService.append_once持久化；同一主Run只允许一次真正派发，派发意图和成功投递分开。无执行能力的闲聊初判可改判为派发或澄清，追加决议事件而非改写旧记录；实际执行或投递后决定固定。按主Run生成稳定幂等键，崩溃重试继续同一派发，不产生第二个子Run。意图提交后不改派或偷偷降级为自己执行；失败如实展示、可重试同一目标。
5. 普通一次性请求复用`send_mention_message`的原Bot会话/Run/回执，不新建Objective或周期。新建Bot、显式周期和托管原任务仍由原管理工具处理。
6. 当前文本与引用支持自动派发；带附件的主会话先走direct，保留附件执行上下文，不悄悄丢附件。多领域首版一次只选一个明确承接者，歧义澄清，不无依据扇出或串行重复执行。
7. 工作流门控先于实际工具执行：决定前只允许路由及只读目录；direct后恢复主助理原工具策略；派发后阻止重复执行、轮询和二次派发。主聊天现网Claude SDK实现工具与结束门控；DeepAgents复用相同工具门控。Codex入口现有平台派发工具未接通，本轮不宣称支持此入口自动路由。
8. 使用现有发送/接收时间线与SSE。服务端投递事件让前端跟踪真实子Run，主会话不等待；子助理显示“消息来自·主助理”，直接工作并回答。失败/不完整结果不压成成功。

## 验收与发布

- 同一句天气自然提问在不含@/Bot名时交给天气提醒；编码、行业职责以及新增自定义职责用同一目录协议，纯闲聊/不匹配可direct，不建定时规则。
- 真实AG-UI投递、原历史保留、一次主请求一个子Run、重复/并发/崩溃恢复、暂停/归档/撤权、跨账号、引用与带附件处理覆盖测试。
- 门控覆盖决定前WebSearch、dispatch后重复WebFetch/命令、direct正常执行，以及普通任务/项目/子助理自身不受影响。
- 79发布前校验当前compose与无活动Run，备份并保留原数据/VM。安装包hash核验；正常登录浏览器真实自然提问、来源跳转、回传与刷新。结果与限制写入报告，并同步飞书。

## 实机发现后的直接处理收口

首轮模型把“即时查询自己做更快”当作direct理由，说明只记录一个自由文本理由仍不够。direct现细分conversation/no_match/management/attachments/user_requested_self：纯聊天不能调用执行工具；管理只允许管理工具；附件须有真实输入附件；亲自处理须引用输入中的明确自处理要求；无匹配须逐项给出当前目录全部Bot的领域不相关理由。简单、短或快都不是绕过领域助理的依据。目录中“提醒/监控”是长期触发方式，不排斥同领域的一次性查询。依然由模型理解语义，服务端执行分类约束；未引入天气词表或另一个分类模型。

第二轮实测发现“闲聊”误判被门控挡住后又被过早冻结。现允许该无外部执行能力的初判改判为派发/澄清，使用唯一settled事件固定实际派发，已投递后不可改派；其他直接执行决定仍固定。主路由模式增加服务端角色前缀并取消工具前强制空泛开场，先路由再给实际回执；宿主Agent权限及原提示内容保留。

既有RunService会把旧上传文件重新带入后续轮次，并以inherited_input_artifact_ids标识。路由只把input_artifact_ids减去该继承集合后的内容当成本次新附件。纯文字请求不因旧文件退回主助理；用户明确要求处理历史文件时，可用原话attachment_request证明该依赖，继续在主会话保留文件上下文。原文件和历史记录不删除。
