KAI 云电脑 / Computer 架构

说明 KAI 中「持久 Computer」（文档也称为云电脑、本人电脑）是什么、它与一次性 Sandbox 有何不同、云电脑与本机电脑如何并存，以及观察、接管、重连和与个人助理的关系。本文与《KAI 个人助理域架构》互为姊妹篇。

阅读约定

架构总则写明部署地址由配置提供，不以主机编号命名产品环境。本文出现的 79、116、32.45 均来自该分支已提交的实施与验收文档，只表示当时记载的部署实例。镜像标签、摘要和容器健康状况具有日期，后文会标明「截至某日文档」，避免把某一天的现场快照写成永恒现状。

1「云电脑 / Computer」在 KAI 中是什么

源码把该对象定义为：持久的、属于机主的电脑，与一次性 Run 沙箱不同。一个 Computer 按 (tenant_id, user_id) 唯一，拥有稳定的 computer_id、provider、镜像摘要、工作盘引用 volume_ref，以及状态、epoch 与 revision。重建实例后仍应能指向原用户工作盘；稳定身份不等于进程内存也可恢复。

出处：src/harness/computer/__init__.py — 模块说明：“Persistent owner computers, distinct from disposable Run sandboxes.”

出处：src/harness/computer/models.py — AssistantComputer 字段；并写明租约到期是失去许可，不足以证明旧进程已停止。

2026-10-27 的方案把产品模型概括为：「每个用户一台持久 Computer，多个 Agent 共用本人工作环境」。79 充当控制与调度节点；工作机可以先落在 79 的隔离执行资源上，再扩展到独立执行节点。逻辑独占工作机不等于独占一台物理服务器。同用户 Agent 共享文件被写成显式产品边界；第三方 Apps 仍按独立授权控制。

出处：docs/plans/2026-10-27-assistant-dot-bot-computer.md — 目标架构、Computer 对象建议，以及一人一机模型。

1.1当前代码中的状态

代码枚举的 Computer 状态为：registered、starting、idle、running、recovering、failed。2026-10-27 方案曾建议在 Provider 实际支持并验收后再启用 pausing / paused / resuming；现行枚举中没有这些状态。远程电脑计划也写明「尚无真实 OS 睡眠 / 唤醒能力」。

出处：src/harness/computer/models.py — ComputerState 枚举。

出处：docs/plans/2026-11-03-remote-computer.md — 「尚无真实 OS 睡眠／唤醒能力」。

执行许可通过 ComputerLease 发放，用途为 start、execute、recover。源码强调：过期租约必须先在 provider 侧完成 fencing，才能把电脑交给下一次执行；「expiry alone never makes a computer reusable」。

出处：src/harness/computer/registry.py — claim / recover / finish 语义；Registry 是内部控制面，不接受用户传入的 endpoint 或 computer id 作为授权。

2与一次性 Sandbox 的区别

平台架构说明中的 Sandbox 服务于普通任务执行，提供方随部署变化，文档提到过 Daytona、E2B、Kubernetes/gVisor、显式本地模式，以及 OpenSandbox、CubeSandbox。79 的默认任务执行在 2026-10-27 被记载为 opensandbox；116 在 2026-11-04 因到不了 79 的 OpenSandbox，改把 HARNESS_SANDBOX_PROVIDER=cubesandbox。

出处：docs/architecture.md — Sandbox 提供方与执行位置。

出处：docs/plans/2026-10-27-assistant-dot-bot-computer.md — 当时 79 默认 opensandbox，provision 按 run_id、结束 destroy，尚未绑定为用户电脑。

出处：docs/results/2026-11-04-116-acceptance-host.md — 116 改用 cubesandbox 的原因。

早期方案要求：普通临时任务可继续使用既有沙箱生命周期；个人助理经由专用 Provider 适配器接入持久电脑。后来的共享桌面验收进一步写明：已获电脑访问的自有 Bot 会话缺省继承当前执行电脑，但显式 sandbox、普通任务和项目会话保持原边界。因此不能把「打开了电脑面板」理解为所有 Run 都在持久 Computer 里执行。

出处：docs/results/2026-11-05-bot-shared-vm-desktop.md — 继承规则与例外。

3云电脑与本机电脑

对外，用户只看到运营配置好的 opaque target_id 与名称，例如文档中的 cloud 与 local-32-45，看不到主机、路径或密钥。代码要求 provider 只能是 vm-computer 或 remote-computer，镜像必须是 sha256: 摘要。查看接口用 (provider, image, volume_ref) 全等匹配当前 Registry 行，以决定 active_target；匹配失败时 active_target 为空。

出处：src/harness/computer/targets.py — opaque target、idle-only 切换委托给 Registry，公开字段不含端点。

出处：docs/plans/2026-11-03-remote-computer.md — ComputerRegistry 是执行绑定的唯一事实来源；只读切画面不改变执行机。

3.1云电脑（vm-computer）

2026-11-05 的演示文档把云电脑描述为 79 上的 QEMU/KVM qcow2 虚拟机（当时容器名记为 kai-computer-owner-preview-20261027）。桌面在客户机内。更早的桌面 VM 验收说明：独立 KVM guest 已能启动，Chromium 可保持自身沙箱；桌面与终端使用不同身份，终端任务回收不结束浏览器；更换 runner 或再次开机后，浏览器本地数据与 HOME 文件可保留。该文同时声明：当时它仍是独立 fixture，不等于本人工作卷已全部迁入，也不等于观察 / 接管已在该 fixture 上完成验收。

出处：docs/results/2026-11-05-kai-computer-demo.md — 云电脑形态与 D3 实证（hostname 显示 Chassis: vm）。

出处：docs/assistant-computer-desktop-vm-20261027.md — 早期独立 KVM guest 验收与未完成项（若需对照日期，见该文档标题）。

2026-11-05 的共享桌面结果补充：VM 内有可见桌面和受执行租约约束的后台 shell，二者属于同一台 VM；桌面账户与任务账户的 HOME / 权限是分离的，不能由「同一台机器」推出桌面文件管理器可直接访问任务工作区。GUI 优先复用可见浏览器及其会话；明确要求的后台测试或纯文件处理可以无窗口完成。

出处：docs/results/2026-11-05-bot-shared-vm-desktop.md — 共享 VM 桌面的能力边界。

3.2本机电脑（remote-computer / local-32-45）

local-32-45 是文档中的目标 ID，对应用户授权接入的本机 192.168.32.45。因为实测 79 不能主动连接该主机，采用本机发起到 79 的反向 SSH Unix socket。专用 link 账号只允许远程 Unix 转发，禁止 TCP 转发、TTY 和普通命令。桌面密钥只能转发本人当前 :0 桌面的私有 Unix RFB socket。凭证不得写入聊天、仓库或模型上下文。

本机执行复用原 supervisor 的 UID 28000、PID/mount namespace 和执行租约。独立 SSH 控制密钥只能进入固定 root gate。远程电脑计划还记载：32.45 随后升级到 Ubuntu 24.04.5 LTS，并接入原生 computer_ui（复用 DesktopService 的权限、租约和接管屏障）。云电脑仍走原路径。安装 CLI 或辅助功能树探测，不能等同于模型端能力已经齐备；当时模型端到端仍待用户验证。

出处：docs/plans/2026-11-03-remote-computer.md — 反向通道、权限边界、24.04 升级与 native desktop 发布范围。

3.3历史形态：Docker Computer

在 VM / Remote 之前，V0 使用独立 Docker Computer 驱动：注册、互斥租约、Manager、固定监督器，并在 79 验证过受控执行复用、心跳与失联恢复保留工作盘。控制面代码仍包含 docker-computer 路径，且写明电脑不暴露 execd，只有控制面能以 root 调用固定监督器，模型命令被降到专用任务 UID。本文把 Docker 电脑视为已经实现过的提供方，不把它自动等同于当前 79 演示里的「云电脑」——演示文档将当时的云目标记为 vm-computer。

出处：docs/plans/2026-10-27-assistant-dot-bot-computer.md — V0 Docker 驱动与后续 V1 桌面计划。

出处：src/harness/computer/control.py — 「These computers expose no execd service」以及 DockerComputerControl。

4控制面、Registry 与目标切换

ComputerRegistry 是供助理执行的电脑绑定唯一事实来源。所有写入先锁机主行；数据库时间在加锁之后采样，避免排队或时钟偏差给过期持有者续命。Provider I/O 不得占用该事务。这是内部控制面，调用方必须先解析已认证机主。

switch_provider 是已有机主行更换机器的唯一途径：要求电脑空闲且没有活的 holder，保留稳定 computer_id 与历史，拆掉旧 provider 实例引用，但不在此删除或覆盖旧工作盘。若桌面仍处于非 observe 且未到期，必须先交还控制权。活跃 Run 期间切换，演示文档记录返回 409「电脑正在使用中」；租约过期后可自动释放，文档不建议手工清库。

出处：src/harness/computer/registry.py — ensure / adopt / switch_provider / claim 语义。

出处：docs/results/2026-11-05-kai-computer-demo.md — idle-only 切换与 409 实证。

代码还允许按 Bot 桌面槽位（ComputerDesktop，位于机主 VM 内）单独发放执行租约：整机执行与某个 Bot 桌面执行互相排斥；两个桌面的 epoch 互不失效。是否每一套部署都启用了「一 Bot 一屏幕」，要以该环境的验收文档为准。2026-11-05 的共享桌面验收主要证明的是：多个已授权 Bot 可以共享机主当前这台 VM / 桌面，同时账户目录仍然隔离。

出处：src/harness/computer/models.py — ComputerDesktop：「One Bot desktop inside an owner's VM。」

出处：src/harness/computer/registry.py — _scope_is_current：桌面租约按槽位 epoch 校验。

5观察、接管与重连

执行租约决定谁可以跑命令；桌面控制服务决定谁可以触碰可见桌面。二者分开。桌面状态为：

  • observe：观察；
  • agent：助理持有键盘和指针；
  • takeover_pending：用户请求接管，双方新输入被挡住，节点停止并排空尚未完成的动作；
  • human：仅在节点 confirm_human 之后发布。

每次改变输入权的人都使 epoch + 1，GUI 动作必须带上所观察到的 epoch，过期发送者会被拒绝。Pending 窗口到期且未得到 drain 确认，只能回落到观察——接管不能只靠计时器成功。人工或助理所有权到期后，也是惰性回落到 observe。

现行代码中 HUMAN_TTL_SECONDS = 90（打开的 viewer 每秒续期，窗口只需覆盖一次重连；过长会让崩溃标签页的租约长时间挡住下一个窗口）。AGENT_TTL_SECONDS = 120。若执行租约仍被某个 Run 持有，对默认桌面 vm 的接管会被拒绝，并提示先等任务结束或中止。

出处：src/harness/computer/desktop.py — 状态机、TTL、epoch 与 binding 校验的模块文档与实现。

5.1已记录的接管 / 重连故障

2026-11-11 的对齐文档记录了两类「能看不能接管 / 重连循环」问题，并给出已落地的修复说明：

  1. 查看的不是执行电脑：接管只对助理当前使用的电脑有效。若 viewTarget !== active_target，viewer 按当前画面目标读到 observe 并丢弃输入，但界面可能仍写「由你控制」。修复是改提示为「当前画面仅观看」，并提供切回执行电脑。
  2. 租约绑在已消失的 viewer：viewer_id 若每次挂载都随机生成，刷新即变成新 viewer，旧租约仍为 human。前端会认为「另一个窗口已接管」，按钮被禁用；短命连接若在成功时清零重试计数，可能无限重连。修复包括：viewer id 存入 sessionStorage；连接稳定 10 秒后才更新重试预算；把人工 TTL 从 300 秒改为 90 秒。
  3. 镜像摘要不一致导致 active_target 为空：若 HARNESS_ASSISTANT_COMPUTER_TARGETS 里 cloud 目标的 image 与注册表当前 HARNESS_ASSISTANT_COMPUTER_VM_IMAGE 不一致，view() 匹配失败，前端拿不到 binding_key，出现「电脑已切换，正在重新确认控制状态」，接管按钮被禁用。文档记载 79 已把两处 cloud image 改成一致。

出处：docs/plans/2026-11-10-assistant-parity-1-2-3-7.md — 79/116 同步部署与接管、重连问题及修复。

该文档同时写明：修复已随 79 的 web / viewer 发布；116 当时只升了 web，viewer 仍跑旧 api 镜像，接管租约 TTL 仍是 300 秒。若要把 116 做成与 79 一致，需要连同 api/viewer 一起重建。本文不以 79 的代码默认值，去覆盖 116 现场是否已经赶上。

6本机反向通道与安全边界

远程电脑计划记载的运维边界包括：79 的 control 与 viewer 保留 cap_drop ALL；反向 Unix socket 目录使用专用 link 用户、root 组、权限 2750；socket 为 link:root、0660；容器通过组访问，不新增 DAC 能力，也不开放 TCP 桌面端口。Viewer 在每次键盘、指针或剪贴板输入时重新核验当前人工控制 epoch，拒绝交还后旧连接继续输入。

演示文档把两条通道写得更具体：执行走 control 身份的 remote_gate.py（identity / activate / deactivate / acp / native_desktop 等）；画面走 remote_display_gate.py。两条 SSH 身份、两套 authorized_keys，互不越权。ACP 在桥接进程里降权到桌面用户（PR_SET_NO_NEW_PRIVS 等），凭据不复制、不给 root。gate 每次按启用组件集合重算摘要，并与 /etc/kai-computer-remote.json 的 image 比对；组件与摘要必须一起更新。

出处：docs/plans/2026-11-03-remote-computer.md — 通道权限与 epoch 再校验。

出处：docs/results/2026-11-05-kai-computer-demo.md — gate、digest pin 与 ACP 降权。

6.1已记录的连接类故障

  • 2026-11-05：共享声明文件 /etc/kai-computer-remote.json 为 root:root 0640，桌面用户无法读取，viewer 握手失败（WebSocket 403）。修复为 root:桌面用户主组 0640，不改摘要或密钥。
  • 同日复发：SSH ProxyCommand 辅助进程退出后变成容器 PID1 下的僵尸进程，耗尽 pids 额度。修复是给 computer-control / computer-viewer 启用 init: true 收养孤儿进程；重启只能清积累，不能代替回收修复。
  • computer-control 的 BlockingIO 卡死在演示计划中被记为复发型，重启可恢复，但应排查泄漏。

出处：docs/results/2026-11-05-local-computer-recovery.md — 声明属组与进程回收。

出处：docs/plans/2026-11-05-kai-computer-demo-pipeline.md — D1 BlockingIO 备注。

7与个人助理域的关系

个人助理（主助理与专职子助理）是编排入口，Computer 是本人工作环境。典型路径为：用户在 /assistant 与主助理或子助理对话 → 已授权会话调用 computer_* / computer_ui / computer_acp 等工具 → Worker 访问 computer-control → 按当前执行目标进入云 VM 或本机 gate。

职责若声明需要共享可见桌面，会进入单执行者队列（优先级 + FIFO，不抢占活 holder）；助理页可在占用出现时自动展开电脑面板（能力 7）。首屏不应自动连接桌面。这些规则的产品含义见姊妹篇 《KAI 个人助理域架构》。

出处：docs/plans/2026-11-04-assistant-startup.md — 电脑延迟连接与 personal_computer 授权。

出处：docs/plans/2026-11-10-assistant-parity-1-2-3-7.md — 自动展开云电脑。

两条执行通道不要混说（截至 2026-11-05 演示文档）

本机 computer_acp 是机主桌面用户身份下的 Claude/Codex 子代理，写的是机主机器、用的是机主登录态。云上 Bash / 文件工具在当天实测中走沙箱策略。该文档要求演示话术加以区分。未见后续总文档宣布这一边界已被废除。
