云电脑与远程电脑架构对照：KAI · OpenMausBot

对照结论

差在「电脑跟账号走还是跟 Bot 走，以及多人抢同一块屏幕时怎么排队」。不要把本文读成 KAI 云电脑操作手册。
  • KAI 电脑是账号级执行环境：云桌面与远程电脑（含 local-32-45）可切换，但同一时刻共享桌面只有一个执行者。查看目标与执行机分开；占用按优先级降序加 FIFO 排队，活的 holder 不被硬抢。人工接管有租约：当前分支代码里 HUMAN_TTL_SECONDS = 90；文档记录 79 已按 90 秒发布，116 的 api / viewer 当时仍是 300 秒。
  • OpenMausBot 默认「每个 Bot 可以有自己的电脑」：云端 Linux 桌面、隔离的 Local VM，或在明确开启后使用「这台电脑」。高风险操作走聊天里的审批卡。本机控制由 Electron 托管的 CUA 驱动负责；云端 turn 可进入 bubblewrap「bot box」。Local VM 在 bot box 开启时不可用，因为不能把 Docker 套接字送进盒子。
  • Grok Bot 今晚群内没有说明电脑内部结构。OpenMausBot README 的对照表将其概括为「一份花名册共用一台云电脑、只用 Grok」。这是对方主张，不是已核实的内部调度、租约或 viewer 协议。细节标为未在公开资料中找到。

三方怎么放置电脑

KAI

账号共享桌面，控制面管生命周期与权限

ComputerRegistry 是助理当前执行电脑的唯一事实来源。运营配置声明可选目标，API 只暴露不透明的 target ID 与名称。平台继续只管生命周期、权限与消息，不把业务流程写进电脑层。

OpenMausBot

Bot 自带电脑，本地优先也可上云

云桌面走已有 computer-proxy（Boat）；本机走 Electron 主进程拉起的 cua-driver，harness 只拿到校验过的 MCP 代理，自己不生成驱动。浏览器优先用应用内嵌的 Chromium。

Grok Bot

只有间接表述

公开对照声称是「共享云电脑」。今晚群内自述只覆盖频道应答，没有电脑队列、租约或显示协议。本文不画未核实的内部箱。

归属与隔离

维度KAIOpenMausBotGrok Bot
电脑跟谁走 跟账号的当前执行电脑走。已获电脑访问的自有 Bot 会话缺省继承该执行电脑；普通任务 / 项目、未授权或显式沙箱保持原边界 跟每个 Bot 走。云桌面、Local VM 或「这台电脑」是 Bot 资料的一部分 OpenMausBot 称其为「一台共享云电脑」。官方内部模型未找到
多执行者冲突 共享桌面单执行者；队列 = 优先级降序 + FIFO；occupancy 投影位次与原因；对活 holder 不硬抢。软抢占（把剩余 TTL 钳到 30 秒）在计划里写为已落地，当时注明尚未部署 79 未在 computer-use 文档中找到与 KAI 对等的跨 Bot 共享桌面排队模型。房间对电脑的约束，runtime-contract 只写到「房间电脑上限是准入」一层，细节未在本对照中展开为完整队列 未在公开资料中找到排队或单执行者规则
隔离边界 云 VM 的桌面账户与任务账户 HOME 分离；不能由「同一台机器」推断桌面文件管理器可直接访问工作区。远程机经反向 SSH Unix 套接字接入，凭证不进聊天 / 仓库 / 模型上下文 云 turn 的 bot box：bubblewrap 用户命名空间，只放回本轮工作目录与该 Bot 自己的文件夹；出站走 egress 门，密钥可换成经纪代币。本机「这台电脑」是另一条 CUA 路径，需一次性明文征求同意 隔离实现未在公开资料中找到
本地 / 远程形态 云 VM 保留；用户可授权把 192.168.32.45 接为 Remote Computer（目标 ID local-32-45）。79 不能主动连该机，由本机反向 SSH。原生 computer_ui / AX 已接到 32.45，与 RFB 共享租约和接管屏障 云端 Boat 电脑与隔离 Local VM 是独立提供方，不被 CUA-only 规则替换。本机控制在 macOS 与 Ubuntu Xorg 明确开启后可用；Ubuntu Wayland 主机控制在 issue #345 解决前保持关闭 是否区分本机与云电脑：未在公开资料中找到

执行与查看路径

KAI 特意把「正在看哪台」和「助理正在用哪台」拆开：只读切画面不改变执行机，必须经「供助理使用」才申请变更执行。这是 2026-11-11 接管困惑的根因之一——查看非执行电脑时输入会被丢弃，但旧文案看起来像已经接管。

图 3　OpenMausBot：三条互不替代的电脑路径

79 / 116 与部署差

KAI 的电脑行为不仅取决于仓库 HEAD，还取决于各环境有没有把 api / viewer 一起升上去。这是对照时必须单独写的一层。

环境文档记录的电脑相关状态（截至 2026-11-11 对齐计划）
79 远程电脑与云桌面均有多轮迭代。2026-11-11 已发布 web desktop-pane5-20261111 与 viewer session-log-20261111，文案含「当前画面仅观看」；接管租约按 90 秒 + viewer 排障日志记录。计划入口（口述、未在本页探活）：https://172.20.105.79:3543/assistant
116 同步时只升了 web，api / worker 镜像未变；文档写明「116 的 viewer 仍跑旧 api 镜像，接管租约 TTL 仍是 300 秒。若要和 79 一致（90 秒 + 排障日志），下次连同 api / viewer 一起重建。」待办列表再次写：「116 的 api / viewer 仍未带 90 秒接管租约与 viewer 排障日志（当前只有 web 修复）。」本对照未再登录 116 复核之后是否已补做。

当前分支源码中的默认值已经是 90 秒；把「代码默认」直接说成「116 现网行为」会与部署记录矛盾。

与助理域的边界

助理是谁、群里谁开口，见伴生文档 助理域架构对照。本文只保留电脑边界上的几条，避免把路由写进来：

  • KAI：电脑占用可以带动助理页自动展开，但不改变 1:1 发送或群应答规则。
  • OpenMausBot：每个 Bot 的电脑权限是 Bot 资料的一部分；部门分享明确不带电脑权限。
  • 群组若共享桌面，KAI 今晚口径是沿用现有单执行者队列，而不是按房间另做一套执行机。此条来自既有对照分析与占用设计，不是新的现网结论。
