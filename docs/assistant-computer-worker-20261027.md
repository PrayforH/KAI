# Computer V0：Worker 作用域与长期工作盘

2026-10-27，北京时间。接续 [Manager 组件验收](assistant-computer-manager-20261027.md)。本轮接入通用 Worker 编排层并在 79 使用隔离电脑运行验收；生产配置尚未选用新 Provider，生产数据库仍为 0050。没有将确定性测试运行时的成功当作本人助理真实模型验收。

## 实现

新增 `ComputerSandboxProvider`，实现现有命令和文件工具接口，并提供 Run 作用域。Worker 的状态机拆为取得执行权和已分配环境内的执行两个阶段；可选的 Provider 作用域包住后者及清理过程，原 Provider 沿用原流程。

普通文字聊天只分配临时本地镜像目录，不创建或重连电脑。首次工具调用才通过 Manager 取得本人电脑租约、记录远端文件基线、上传本轮输入。心跳任务属于该 Run 的结构化任务组；心跳失败会取消运行时，而不只是等待下一条命令碰到无效权限。运行结束、停止或 Worker 任务关闭时，先确认物理执行清理，再释放电脑租约；不会删除本人电脑实例和工作盘。

`SandboxHandle.persistent_workspace` 是 Provider 生成的事实，不接受模型请求作为路由依据。Worker 据此跳过 Session 旧快照恢复和局部镜像归档：远端工作盘是长期文件来源，本地目录只是本轮输入与收集结果。这样既不把旧快照覆盖到电脑，也不把只含部分文件的本地目录当作下一轮完整工作区。

新增 `ComputerWorkspace` 和只依赖标准库的远端文件实现 `workspace_guest.py`：

- 文件操作仍经固定监督器降权，使用当前执行租约；没有另开 root 文件 API。
- 按目录描述符打开路径，拒绝绝对路径、`..` 和符号链接穿越；只读取普通文件，不阻塞在 FIFO 等特殊文件上。
- 2 MiB 分块传输，上传先写临时文件，校验完整 SHA-256 后原子替换；下载核对文件版本及完整校验和，拒绝传输中变化或截断的数据。
- 首次使用时记录基线，只收集本轮新增、修改的文件；多次收集时只清理本轮已收集但远端已删除或恢复原内容的本地副本。收集不删除远端文件。
- 自动产物归属合并远端基线，避免把此前生成的报告再次发布为本轮新产物；按需下载的旧文件仍可供显式文件工具使用。
- 上传只来自新建的本轮目录，保留输入及必要 Agent 资源。Worker 的 `.harness-runtime`、`.tmp`、`.git` 不上传，避免把 SDK 控制配置和临时凭据带到工作盘。扫描还排除依赖和内部目录，并保留成员数、字节数上限。

目前不能强制执行按域名限制的出站策略；收到限制性 egress 要求会拒绝执行。新后端也没有被标记为 full enforcement。路由接入时须继续遵守现有发布配置与 Session 信任门槛，不能借“个人电脑”绕过执行策略。

## 验证

本地集成使用真实 PostgreSQL Computer 注册与租约、真实 Worker 状态机和真实 fixture 文件；物理驱动模拟，模型运行时确定性生成，因此该部分不证明远程进程隔离。

1. 两轮 Run 使用相同电脑和工作盘，前轮项目文件可读取，结束后电脑为空闲；旧 Session 恢复和本轮局部归档均未调用，旧报告没有重复发布。
2. 纯聊天完成后没有 Computer 注册记录，也未调用物理驱动。
3. 物理心跳失败取消挂起运行时，确认清理并释放租约。
4. 停止正在执行的 Run 后，返回 cancelled 前完成清理，工作盘内容保留。
5. Worker 执行任务被取消后留下可恢复的 Run；再次接续复用原电脑和文件。

文件测试覆盖多块及空文件、执行权限保留、校验失败不覆盖原文件、传输中变化、路径穿越、远端和本地符号链接、特殊文件、旧产物基线和 Worker 控制目录不外传。合并既有编排、延迟沙箱与执行策略回归见[测试结果](results/assistant-computer-worker-20261027/tests.txt)。

79 验收使用真实 `RunOrchestrator`、真实 Docker Computer 与 UID 28000，Run/Event/Artifact 仓库为内存 fixture，运行时为确定性测试实现；不是生产账号或真实模型：

- 纯聊天不分配电脑。
- 3.6 MB 文件与空文件上传下载逐字节一致。
- 两轮分别创建新的 Provider，仍使用同一实际容器及工作盘，上一轮项目、报告和用户目录可执行工具均保留。
- 第一轮仅发布 `outputs/first.txt`，第二轮仅发布 `outputs/second.txt`。
- 收尾删除仅含 fixture 的实例和两块卷，停止隔离数据库、控制器和测试客户端，删除生成的测试密钥；未向生产 API 容器复制代码或配置。

证据：[79 实测](results/assistant-computer-worker-20261027/worker-probe-79.json)、[环境及源码指纹](results/assistant-computer-worker-20261027/environment.json)、[清理](results/assistant-computer-worker-20261027/cleanup-79.json)、[生产账号/绑定/原历史记录保留](results/assistant-computer-worker-20261027/production-verification.json)。生产服务仍使用原镜像。

上轮 `environment.json` 曾把代码默认资源值记为测试分配值，本轮按当时实际 `controller.env` 修正为 512 MiB / 0.5 CPU；代码默认值仍为 4 GiB / 2 CPU。本轮隔离试验也使用 512 MiB / 0.5 CPU。该数值不表示生产桌面的最终容量。

## 上线前仍需完成

1. 生产路由只从数据库中的本人账号、租户成员关系和个人助理线程解析电脑归属；保留线程历史 Session，不能按模型输入里的开关决定。
2. 内部控制节点校验真实账号状态、Run / Session、当前 Worker 执行归属及电脑租约；取消或失去业务访问权后拒绝新执行，允许必要的停止清理。当前受控试验只验证电脑租约，不能替代这些业务检查。
3. 配置固定镜像、节点服务、资源准入和密钥注入；把电脑与临时沙箱清理归属分开。限制网络或要求更强隔离的任务须明确拒绝不满足的后端。
4. 处理需要 remote CLI 的运行时、父子 Run 的电脑权限继承或调度；不能让父任务持有电脑时等待竞争同一电脑的子任务。
5. 在 79 本人助理做真实模型两轮任务、运行停止和 Worker 重启验收，再核对飞书、微信、网页同会话与刷新续聊，保留原绑定和历史。
6. 后续浏览器桌面、真实登录 profile/keyring、鉴权观察和接管互斥仍按原方案推进。本轮未实现桌面或保存进程内存。
