## 1. 现象

用户反馈「知识库做了更深的 wiki 配置，现在 173 部署的版本没有」。核对确认 173 上知识库新建/配置表单里的 `分块设置` 与 `Wiki 设置` 两个区块整体消失。

## 2. 根因

**是本次的三个 web 部署把它覆盖了**，机制如下：

1. 该功能属于**未提交**的在途改动：`wikiContentInstructions` 在 HEAD 中出现 0 次，在工作区出现 6 次且全部是新增行（同属 `knowledge-console.tsx` 的 `分块设置` / `Wiki 设置` 亦为新增）。
2. 本项目的 web 镜像**从工作区全量构建**，tag 只是标签、并不代表某个提交。事故前在跑的 `no-upgrade-banner-20260910`（digest `23fa9cf7fd49`）虽以提交 `c9df6f6` 命名，实际含有这些未提交改动。
3. 我为「不自作主张发布别人未完成的工作」而改用**独立 worktree（HEAD + 仅本人改动）**构建镜像。这个判断的前提——「线上镜像对应某个已提交状态」——在本项目不成立，于是新镜像把未提交的知识库改动整块替换掉了。

## 5. 教训与后续约束

1. **本仓库的「线上版本」= 工作区全量构建**。tag 名只是标签，不能据此推断内容对应哪个提交。
2. **不要为了“只发布自己的改动”而把 web 构建范围收窄**：那等于把别人在途的未提交工作一起回退。
3. 若确有需要收窄构建范围，**先验证线上镜像不含未提交改动**：对上一版镜像 grep 1–2 个在途标记字符串（例如本次的 `分块设置`），确认无命中后再收窄。
4. 部署前对照检查：`git status` 里若存在**未提交的前端改动**，则该镜像必须从全量工作区构建。
5. 更根本的解法是把在途功能提交到分支再发布，避免「工作区状态即线上状态」这一隐式契约。
